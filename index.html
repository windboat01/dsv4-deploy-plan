🏗️推理架构

核心思路：MoE 模型天然适合拆分——稠密层（Attention/Norm/Router）对精度敏感，用 FP8 跑在 GPU 上；MoE 专家层参数量巨大但对量化不敏感，用 INT4 跑在 CPU 多线程上，靠 16 通道 DDR4 内存带宽喂饱。 
ftllm server deepseek-ai/DeepSeek-V4-Flash \
  --device cuda          # 稠密层 → GPU (FP8)
  --moe_device numa      # MoE 专家层 → CPU (INT4, 双路NUMA)
  --dtype fp8            # 稠密层精度
  --moe_dtype int4       # MoE 专家层精度
  -t 1                   # 由 FASTLLM_NUMA_THREADS 控制

关键配置说明

要点说明
为何选 7302 而非更大核心的 CPUMoE 推理瓶颈在内存带宽而非算力，16核/颗刚好把 8通道 DDR4 带宽喂饱。加核心带宽不增加，性价比下降。
为何 16×16GB 而非 8×32GB16 根填满 16 通道，带宽翻倍；16GB 二手价远低于 32GB，同容量总价更低。
为何 DDR4 2400 而非 3200当前行情 16GB 3200 二手溢价过高（¥320 vs 难寻的 3200），2400 有效带宽 ~270 GB/s，足够支撑 15-18 tok/s。
为何 RTX 3090 而非更贵的卡稠密层 FP8 仅需 ~14-18 GB VRAM，3090 24GB 余量充足。1M 上下文时用 KV Cache INT4 压缩即可。
CPU 散热器怎么处理保留附赠的 4U 5热管服务器散热器（鳍片可压 155W）。拆掉原配的 80mm 高转速风扇，用扎带固定两把猫头鹰 NF-F12 120mm 风扇，静音且散热足够。
机箱风扇怎么配PK620PC 采用"下进上出"风道：底部 2×140mm 进风 → 经过 CPU/内存 → 顶部 2×140mm 出风。不用装前后风扇，社区验证对双路 EPYC 效果最佳。
电源选型的注意点长城 G11 ATX3.0 带 2 根独立 CPU 4+4-pin 线，正好插满 H11DSi 的两个 EPS 12V 口。1100W 给双路 7302（310W）+ 3090（350W）余量充足。
机箱选型的注意点H11DSi 是 33.1cm 宽 E-ATX，普通机箱装不下。PK620PC 支持到 33.5cm，已验证兼容。CPU 散热限高 18cm，4U 服务器散热器（~15cm）轻松放下。
GPU 插在哪个 PCIe 槽CPU1 最近的 PCIe 3.0 x16 槽。PCIe 利用率 <1%，插哪都可以。

多并发性能推算

推演逻辑：单次推理的时间拆解

整个架构中一次推理的瓶颈在 CPU 端的专家加载。GPU 端（~8ms）和非核心开销（~7ms）远小于 CPU 端，且多并发时 GPU 可以 batch 批处理，GPU 端延迟不随并发数等比增加。以下推算假设 GPU + 其他开销固定为 15ms。

🧑 单用户（1 并发） 每人 ~16 tok/s ✅
请求独占整颗 CPU0 的 8 通道带宽（~135 GB/s）
CPU 专家加载：13 GB ÷ 135 GB/s = ~96 ms
GPU + 其他：~15 ms
每 token：96 + 15 = 111 ms → 1000/111 ≈ 9 tok/s
👥 2 用户并发 各 ~9 tok/s ✅ 甜点
请求 A → CPU0（8 通道），请求 B → CPU1（8 通道）
两颗 CPU 使用各自的本地内存，带宽完全独立，无竞争
CPU0 带宽 135 GB/s ÷ 请求 A（1 个）= 135 GB/s / req
CPU1 带宽 135 GB/s ÷ 请求 B（1 个）= 135 GB/s / req
每人 CPU 专家加载：13 ÷ 135 = ~96 ms
GPU batch size=2，attention 略有增加：~10 ms
其他开销：~7 ms
每 token：96 + 10 + 7 = 113 ms → 1000/113 ≈ 各 ~9 tok/s
系统总吞吐：~18 tok/s（带宽利用率接近双路上限 270 GB/s）
👤👥 3 用户并发 各 ~6 tok/s
请求 A → CPU0，请求 B、C → CPU1（某 CPU 上挂 2 个请求）
CPU0 带宽 135 GB/s ÷ 1 个请求 = 135 GB/s / req → ~9 tok/s
CPU1 带宽 135 GB/s ÷ 2 个请求 = 67.5 GB/s / req
较慢的请求（CPU1 上）：13 GB ÷ 67.5 GB/s = ~193 ms
GPU + 其他（batch=3，约需 ~13 ms）
每 token（拖后腿的那个）：193 + 13 + 7 = 213 ms → 1000/213 ≈ 各 ~5 tok/s
系统总吞吐：~16 tok/s。两个快的请求会被慢的那个拖到同一速度（同步调度）。
👥👥 4 用户并发 各 ~5 tok/s
每颗 CPU 上均分 2 个请求，带宽各被平分
CPU0 带宽 135 GB/s ÷ 2 个请求 = 67.5 GB/s / req
CPU1 带宽 135 GB/s ÷ 2 个请求 = 67.5 GB/s / req
每人 CPU 专家加载：13 ÷ 67.5 = ~193 ms
GPU batch=4，约需 ~15 ms
每 token：193 + 15 + 7 = 215 ms → 1000/215 ≈ 各 ~5 tok/s
系统总吞吐：~19 tok/s（四路带宽用尽）

汇总

并发数带宽分配每 token 耗时每人 tok/s系统总吞吐体验
1 1 CPU × 135 GB/s 111 ms ~9 ~9 ✅ 快
2 🏆 每 CPU 独享 135 GB/s 113 ms 各 ~9 ~18 ✅ 各不降速
3 某 CPU 被平分为 67.5 GB/s 213 ms 各 ~5 ~16 ⚠️ 可接受
4 每 CPU 各平分 67.5 GB/s 215 ms 各 ~5 ~19 ⚠️ 还可接受
6+ 每 CPU 各被 3 分 <45 GB/s >300 ms <3 ~20+ ❌ 变慢
🏆 关键结论：2 人同时使用是最佳工作点
双路 NUMA 天然隔离——请求 A 走 CPU0，请求 B 走 CPU1，各用各的 8 通道内存带宽，互不竞争，每人体验等于单发。这是双路架构相比单路最大的优势。
📐 公式说明
每 token 耗时 = (13 GB ÷ 可用带宽/请求) + 15 ms（GPU + 固定开销）
可用带宽/请求 = 单颗 CPU 有效带宽(135 GB/s) ÷ 该 CPU 上的请求数
每 tok/s = 1000 ÷ 每 token 耗时（ms）

🚀部署命令

标准启动

export FASTLLM_NUMA_THREADS=16

numactl --cpunodebind=0,1 \
  ftllm server deepseek-ai/DeepSeek-V4-Flash \
    --device cuda \
    --moe_device numa \
    --dtype fp8 \
    --moe_dtype int4 \
    -t 1 \
    --port 8080

模型导出（避免每次启动在线量化）

ftllm export deepseek-ai/DeepSeek-V4-Flash \
  -o /models/dsv4-flash-fp8-int4 \
  --dtype fp8 --moe_dtype int4 \
  -t 32

1M 上下文场景

ftllm serve /models/dsv4-flash-fp8-int4 \
  --device cuda --moe_device numa \
  --max-model-len 1048576 \
  --kv-cache-dtype int4 \
  --port 8080
